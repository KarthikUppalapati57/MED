Where Data Comes From

Supabase table: products RPC: get_trusted_global_vendor_item_suggestions RPC: get_flagged_vendor_items RPC: resolve_price_variance Realtime: products

Main product rows are read through api.entities.Product.list(), which wraps supabase.from('products') and auto-applies active organization, brand, and location scope where available.

The AI Verification Queue reads trusted network suggestions using supabase.rpc('get_trusted_global_vendor_item_suggestions'). The Price Action Center reads vendor item price spike rows through api.vendors.getFlaggedVendorItems(organization.id).

Frontend Processing

  1. Route tab is derived from /Products/:subPath, defaulting to all-products.
  2. Search is debounced for 500 ms, then Product list is paged in blocks of 50 rows.
  3. Category filtering happens client-side against accounting_category.
  4. Trusted global matching tokenizes the tenant product name and global item name, requires high token overlap, mapping count >= 50, and confidence >= 90.
  5. Create, update, delete, and bulk delete all invalidate the products query cache and rely on soft delete behavior in api.entities.Product.
  6. Realtime subscription on public products invalidates the product cache whenever any product row changes.

Create / Edit / Delete Workflow

  1. User opens Add/Edit Product. Ground staff are hidden from management buttons by UI permissions.
  2. Form writes name, product_id, description, category, accounting_category, inventoried/tax flags, units, price, and location-specific flag.
  3. Create uses api.entities.Product.create(). If product_id is blank, UI generates PRD-<timestamp>.
  4. Update uses api.entities.Product.update(id, formData).
  5. Delete and bulk delete use soft delete because the Product entity is configured with useSoftDelete = true; the API sets deleted_at.
  6. On success, React Query invalidates products; Supabase realtime also refreshes the product list when the row changes.

AI Verification and Global Mapping Workflow

  1. UI loads product rows and, only on the AI Verification tab, calls get_trusted_global_vendor_item_suggestions.
  2. SQL returns only global rows with mapping_count >= 50, confidence_score >= 90, and a normalized COGS category.
  3. Frontend token-matches product names to global item names and requires at least 80% coverage.
  4. When a trusted suggestion is accepted for review, the product dialog is prefilled with the normalized accounting category.
  5. Save is still a normal product update; the global suggestion is not auto-written without user confirmation.

Price Variance Workflow

  1. Frontend calls get_flagged_vendor_items(p_organization_id).
  2. RPC joins vendor_items to vendors, optional vendor_item_mappings, products, and invoices.
  3. User can dismiss or accept the vendor price change.
  4. resolve_price_variance(p_vendor_item_id, p_update_product) clears vendor_items.price_variance_flag.
  5. If accepted and mapped, the RPC updates products.latest_price to vendor_items.last_price.
  6. Updating products.latest_price fires the recipe margin trigger described below.

Where Data Comes From

Supabase table: inventory wastage_logs count_sheets count_sessions recipes auto_orders RPC inventory metrics RPC count/session/receiving/transfer/POS

Inventory rows are read through api.entities.Inventory.filter(), scoped by organization, brand, and location. The page conditionally loads data only for tabs that need it.

Metrics come from get_inventory_totals. Count completion, receiving, transfer, and POS depletion workflows are server-side Postgres RPCs.

Frontend Processing

  1. Route subpath maps to active tabs such as inventory list, wastage, receiving, counts, POS sync, transfers, and AvT.
  2. Search is debounced for 500 ms; list pages are fetched in pages of 50 rows.
  3. filterByContext narrows returned data to the current organization, brand, and location context.
  4. Realtime invalidation is debounced for inventory, wastage, count sheets, and count sessions.
  5. Inventory table virtualization calculates visible rows from scroll position to keep large lists responsive.

Inventory List CRUD

  1. List loads from api.entities.Inventory.filter() with category, search, sort, and paging.
  2. Edit writes product name, account category, quantity, unit, unit cost, storage location, par level, and reorder point.
  3. Add writes a new inventory row with the same fields and current context scope.
  4. Delete and bulk delete soft-delete rows by writing deleted_at.
  5. Save and delete invalidate inventory queries. Realtime changes also invalidate after a debounce.

Wastage Workflow

  1. User chooses an inventory item and opens Log Wastage.
  2. UI captures quantity, unit, reason, and notes.
  3. Creates a wastage_logs row through api.entities.WastageLog.create().
  4. Then updates inventory quantity and value by subtracting the wasted amount.
  5. Wastage query and inventory query are invalidated; realtime handles other clients.

Count Sheet and Count Session

  1. Create Template builds count_sheets.items from current inventory rows with expected quantity and unit.
  2. Active count session collects counted quantities in the wizard.
  3. Completion calls complete_count_session RPC with organization, location, sheet, counts JSON, and user.
  4. RPC locks rows, calculates variances, updates inventory, creates GL variance entry, creates completed count session, and inserts inventory movements.

Receiving Workflow

  1. Loading Dock loads auto_orders and filters pending/sent/ordered/partially received orders.
  2. User enters actual received quantities. Short quantities are detected client-side for warning text.
  3. receiveOrderWorkflow calls receive_purchase_order.
  4. RPC creates a receivings row, updates auto_orders.status and last_workflow_step.
  5. For each received item, RPC finds inventory by inventory ID, product ID, or product name. It updates existing inventory or creates a new row.
  6. RPC inserts inventory_movements rows with movement_type = purchase_order and source_type = receiving.
  7. Workflow service also creates a notification and emits a frontend workflow event.

Transfer Workflow

  1. Inventory Transfers loads destination locations from api.entities.Location.list().
  2. User selects in-stock inventory items and quantities.
  3. Current component calls execute_internal_transfer directly, creating and completing the transfer in one RPC.
  4. RPC creates a transfers row, deducts source inventory, creates/updates destination inventory, and writes movement rows for transfer out/in.
  5. A separate workflow helper also exists for two-step transfer creation and completion through createTransferWorkflow and completeTransferWorkflow.

POS Sync and Depletion Workflow

  1. Manual POS Sync uploads a CSV PMIX file and parses menu item names and quantities with Papa Parse.
  2. Frontend calls calculate_theoretical_depletion(p_org_id, p_sales_json).
  3. RPC matches sales item names to recipe names, joins recipe ingredients and products, and returns total ingredient usage.
  4. User approves processing; frontend calls execute_inventory_depletion(p_org_id, p_depletion_json).
  5. RPC deducts inventory quantity by product ID and stores previous quantity.
  6. Daily review can call generate_daily_theoretical_usage from pos_sales_data, then approve_daily_pos_usage to deduct and record movements.
  7. Separately, trigger trigger_pos_sales_to_inventory can automatically deplete inventory after insert into pos_sales_data.

Metrics and AvT

  1. get_inventory_totals computes totalItems, totalValue, lowStock, and month-to-date wastage value.
  2. It reads filtered inventory and wastage_logs, enforcing organization/location filters.
  3. get_avt_variance_report exists server-side and aggregates movement rows into theoretical vs actual usage.
  4. The current AvTDashboard.jsx UI uses inventory rows plus generated/mock historical math for display, so it is not yet fully wired to the AvT RPC.

Gaps and Risks

These are not blockers to reading the workflow artifact, but they matter before calling the modules production-complete.

Workflow Risks Found

Inventory movement type mismatch: the earlier inventory_movements check constraint lists stock_count, transfer, and other values, but later RPCs insert values such as count_variance, transfer_in, and likely transfer-out values. If the live constraint was not widened in another migration, count or transfer RPCs can fail at insert time.
  • AvT dashboard is not fully live-RPC-backed: AvTDashboard.jsx currently generates mock opening/purchase/theoretical values from inventory rows. The server RPC get_avt_variance_report exists but is not used in this component.
  • Product Live Dashboard contains seeded/mock events: ProductsLiveDashboard.jsx starts with sample price increase/decrease events, then listens to product updates for simulated realtime costing events.
  • POS sync has multiple paths: CSV upload uses calculate_theoretical_depletion and execute_inventory_depletion; daily review uses generate_daily_theoretical_usage and approve_daily_pos_usage; edge functions write POS orders/tickets; the pos_sales_data trigger can also deplete inventory. These need one canonical operating path to avoid duplicate depletion.
  • calculate-depletion edge function is placeholder-like: it returns success and processed item count but does not currently fetch inventory/recipes or apply depletion.
  • Products/inventory access is partly UI-gated: ground staff buttons are hidden, but final authority comes from RLS/RPC checks. Review final RLS policies before relying on UI role checks.
  • Soft deletes are frontend API behavior: Products and Inventory use soft delete through apiClient, so direct table deletes or other clients may bypass that unless DB rules enforce the same policy.

Recommended Follow-Up Checks

  1. Confirm live inventory_movements.movement_type constraint includes all inserted values from count and transfer RPCs.
  2. Pick one POS depletion source of truth and disable or document the others to prevent double deductions.
  3. Wire AvTDashboard.jsx to get_avt_variance_report if actual reporting is expected.
  4. Replace seeded/mock product live events with real vendor item, invoice, or product price change events.
  5. Add smoke tests for product price variance resolution, count session completion, receiving, and transfer completion.
